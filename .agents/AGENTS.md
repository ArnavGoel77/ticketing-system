## Standardized Relational Schema

### Dependency Order (CREATE must follow this sequence)
```
DEPARTMENTS → EMPLOYEES → TICKETS → TICKET_RESOLUTIONS
```

### Table 1: `DEPARTMENTS` (Owner: Shobit)
```sql
CREATE TABLE DEPARTMENTS (
    department_id    NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    department_name  VARCHAR2(100) NOT NULL,
    location_building VARCHAR2(50)
);
```

### Table 2: `EMPLOYEES` (Owner: Shobit)
```sql
CREATE TABLE EMPLOYEES (
    employee_id   NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    department_id NUMBER REFERENCES DEPARTMENTS(department_id) ON DELETE SET NULL,
    full_name     VARCHAR2(100) NOT NULL,
    email         VARCHAR2(150) NOT NULL UNIQUE,
    role          VARCHAR2(20)  NOT NULL CHECK (role IN ('USER', 'TECHNICIAN', 'ADMIN'))
);
```

### Table 3: `TICKETS` (Owner: Arnav)
```sql
CREATE TABLE TICKETS (
    ticket_id      NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id        NUMBER NOT NULL REFERENCES EMPLOYEES(employee_id) ON DELETE CASCADE,
    issue_category VARCHAR2(50) NOT NULL,
    priority_level VARCHAR2(20) DEFAULT 'MEDIUM' NOT NULL CHECK (priority_level IN ('LOW', 'MEDIUM', 'HIGH', 'CRITICAL')),
    status         VARCHAR2(20) DEFAULT 'OPEN' NOT NULL CHECK (status IN ('OPEN', 'IN_PROGRESS', 'RESOLVED', 'CLOSED')),
    created_at     TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL
);
```

### Table 4: `TICKET_RESOLUTIONS` (Owner: Arnav)
```sql
CREATE TABLE TICKET_RESOLUTIONS (
    resolution_id    NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ticket_id        NUMBER NOT NULL UNIQUE REFERENCES TICKETS(ticket_id) ON DELETE CASCADE,
    technician_id    NUMBER NOT NULL REFERENCES EMPLOYEES(employee_id),
    resolution_notes VARCHAR2(1000) NOT NULL,
    resolved_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL
);
```

## Standardized Seed Data ID Ranges

To allow parallel work without conflicts, each entity uses a fixed ID range:

| Entity | ID Range | Owner | Details |
| :--- | :--- | :--- | :--- |
| `DEPARTMENTS` | `1` – `5` | Shobit | `1: IT Support`, `2: Engineering`, `3: Human Resources`, `4: Finance`, `5: Operations` |
| `EMPLOYEES` (Users) | `101` – `106` | Shobit | Regular users who submit tickets. `role = 'USER'` |
| `EMPLOYEES` (Technicians) | `201` – `203` | Shobit | Tech staff who resolve tickets. `role = 'TECHNICIAN'` |
| `EMPLOYEES` (Admins) | `301` – `302` | Shobit | System managers. `role = 'ADMIN'` |
| `TICKETS` | `1001` – `1008` | Arnav | Tickets with `user_id` referencing employees `101`–`106` |
| `TICKET_RESOLUTIONS` | `5001` – `5004` | Arnav | Resolutions for tickets `1001`–`1004`, using `technician_id` from `201`–`203` |

### Valid Issue Categories
Use one of: `'NETWORK'`, `'HARDWARE'`, `'SOFTWARE'`, `'ACCOUNT_ACCESS'`, `'EMAIL'`

### Valid Priority Levels
`'LOW'`, `'MEDIUM'`, `'HIGH'`, `'CRITICAL'`

### Valid Statuses
`'OPEN'`, `'IN_PROGRESS'`, `'RESOLVED'`, `'CLOSED'`

## Standardized REST API Contract

All endpoints return a JSON envelope:
```json
{
  "success": true,
  "data": [ ... ],
  "message": "Operation successful"
}
```
Error responses use `"success": false` with an appropriate HTTP status code (`400`, `404`, `500`).

### Shobit's Endpoints

| Method | Endpoint | Description |
| :--- | :--- | :--- |
| `GET` | `/api/departments` | List all departments |
| `GET` | `/api/employees` | List all employees. Supports `?role=USER` or `?role=TECHNICIAN` |
| `POST` | `/api/employees` | Create a new employee. Body: `{ "department_id", "full_name", "email", "role" }` |

### Arnav's Endpoints

| Method | Endpoint | Description |
| :--- | :--- | :--- |
| `GET` | `/api/tickets` | List all tickets (joined with employee name) |
| `GET` | `/api/tickets/:id` | Get single ticket with resolution details if resolved |
| `POST` | `/api/tickets` | Create ticket. Body: `{ "user_id", "issue_category", "priority_level" }` |
| `PUT` | `/api/tickets/:id` | Update ticket. Body: `{ "status", "priority_level" }` |
| `DELETE` | `/api/tickets/:id` | Delete/cancel a ticket |
| `POST` | `/api/tickets/:id/resolve` | Resolve a ticket. Body: `{ "technician_id", "resolution_notes" }` |
| `GET` | `/api/tickets/metrics` | Aggregated analytics (COUNT by priority, status distribution) |

## Review 1 Scope Boundaries

### IN SCOPE (Review 1 — 10 marks)
- DDL: `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`
- DML: `INSERT`, `UPDATE`, `DELETE`
- Single-row functions: `UPPER()`, `TO_CHAR()`, `NVL()`
- Group functions: `COUNT()`, `AVG()`, `GROUP BY`, `HAVING`
- Full-stack bridge: Express REST API + React dashboard

### OUT OF SCOPE (Saved for Review 2)
- PL/SQL Triggers, Procedures, Functions
- Materialized Views & Complex Joins
- Concurrency Control / Locking
- Audit Logs
