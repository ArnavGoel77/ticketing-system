## 3. Arnav's Detailed Task Breakdown (Ticket Management)

### Task A1: Schema Extension — `TICKET_AUDIT_LOGS` Table
Create a dedicated audit table to capture every mutation in the lifecycle of a ticket.

```sql
CREATE TABLE TICKET_AUDIT_LOGS (
    audit_id         NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ticket_id        NUMBER NOT NULL,
    old_status       VARCHAR2(20),
    new_status       VARCHAR2(20),
    old_priority     VARCHAR2(20),
    new_priority     VARCHAR2(20),
    action_type      VARCHAR2(10) NOT NULL CHECK (action_type IN ('UPDATE', 'DELETE')),
    changed_by_user  VARCHAR2(100) DEFAULT USER,
    changed_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL
);
```

### Task A2: PL/SQL Triggers
1. **Trigger `TRG_TICKET_AUDIT_TRAIL` (`AFTER UPDATE OR DELETE ON TICKETS FOR EACH ROW`)**
   * Automatically records `:OLD.status`, `:NEW.status`, `:OLD.priority_level`, and `:NEW.priority_level`.
   * Fires whenever an incident's priority is escalated or moved from `OPEN` $\rightarrow$ `IN_PROGRESS` $\rightarrow$ `RESOLVED`.
2. **Trigger `TRG_AUTO_RESOLVE_STATUS` (`AFTER INSERT ON TICKET_RESOLUTIONS FOR EACH ROW`)**
   * Automatically updates parent record `TICKETS.status = 'RESOLVED'` for the corresponding `:NEW.ticket_id`.
   * Guarantees transactional consistency between the resolution and ticket status.

### Task A3: PL/SQL Stored Procedure — `SP_RESOLVE_INCIDENT_TRANSACTION`
* **File:** `sql/04_arnav_review2_plsql.sql`
* **Signature:**
  ```sql
  CREATE OR REPLACE PROCEDURE SP_RESOLVE_INCIDENT_TRANSACTION (
      p_ticket_id        IN  NUMBER,
      p_technician_id    IN  NUMBER,
      p_resolution_notes IN  VARCHAR2,
      p_status_message   OUT VARCHAR2
  );
  ```
* **Execution Logic:**
  1. Validates that `p_ticket_id` exists and is not already `'RESOLVED'` or `'CLOSED'`. Raises user-defined exception `e_ticket_already_resolved` if already resolved.
  2. Validates that `p_technician_id` belongs to an employee with `role = 'TECHNICIAN'`.
  3. Establishes `SAVEPOINT before_resolution;`.
  4. Inserts row into `TICKET_RESOLUTIONS`.
  5. Commits the transaction and populates `p_status_message := 'Ticket #' || p_ticket_id || ' resolved successfully.';`.
  6. Exception block catches errors, performs `ROLLBACK TO before_resolution;`, and uses `RAISE_APPLICATION_ERROR(-20001, SQLERRM)`.

### Task A4: PL/SQL Stored Function — `FN_CALCULATE_RESOLUTION_TIME`
* **Purpose:** Calculates exact resolution turnaround time in fractional hours.
* **Signature:**
  ```sql
  CREATE OR REPLACE FUNCTION FN_CALCULATE_RESOLUTION_TIME (
      p_ticket_id IN NUMBER
  ) RETURN NUMBER;
  ```
* **Logic:** Computes `ROUND((r.resolved_at - t.created_at) * 24, 2)`. Returns `NULL` if the ticket is unresolved.

### Task A5: Explicit Cursor — `CUR_ESCALATE_STALE_TICKETS`
* **Purpose:** An administrative maintenance routine.
* **Logic:**
  1. Declares an explicit cursor over `SELECT ticket_id, created_at, priority_level FROM TICKETS WHERE status = 'OPEN' AND created_at < SYSTIMESTAMP - INTERVAL '2' DAY`.
  2. Iterates using `OPEN`, `FETCH`, and `EXIT WHEN CUR%NOTFOUND;`.
  3. Escalates `priority_level` to `'CRITICAL'`.
  4. Logs progress using `DBMS_OUTPUT.PUT_LINE('Escalated stale ticket #' || v_id);`.

### Task A6: Concurrency Control & Row-Level Locking
* **Implementation:** Add a "Claim Ticket" endpoint using `SELECT ticket_id, status FROM TICKETS WHERE ticket_id = :id FOR UPDATE NOWAIT;`.
* **Demonstration:** If Technician A is investigating a ticket, Technician B attempting to triage it simultaneously receives `ORA-00054: resource busy and acquire with NOWAIT specified`.

### Task A7: Database Views & Materialized Views
* **View `V_INCIDENT_LIFECYCLE_SUMMARY`:** Joins `TICKETS`, `EMPLOYEES` (requester), `TICKET_RESOLUTIONS`, and `EMPLOYEES` (resolver) into a standardized view.
* **Materialized View `MV_TICKET_SLA_METRICS`:** Pre-aggregates incident volume by category and priority for high-speed dashboard analytics.

## 4. Shobit's Detailed Task Breakdown (Identity & Organization)

### Task S1: Schema Extension — `EMPLOYEE_AUDIT_LOGS` Table
Create an organizational audit table to monitor personnel movement and role escalations.

```sql
CREATE TABLE EMPLOYEE_AUDIT_LOGS (
    audit_id         NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    employee_id      NUMBER NOT NULL,
    old_department_id NUMBER,
    new_department_id NUMBER,
    old_role         VARCHAR2(20),
    new_role         VARCHAR2(20),
    modified_by_user VARCHAR2(100) DEFAULT USER,
    modified_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL
);
```

### Task S2: PL/SQL Triggers
1. **Trigger `TRG_EMPLOYEE_AUDIT_TRAIL` (`AFTER UPDATE ON EMPLOYEES FOR EACH ROW`)**
   * Fires when `role` or `department_id` is updated.
   * Inserts `:OLD.role`, `:NEW.role`, `:OLD.department_id`, and `:NEW.department_id` into `EMPLOYEE_AUDIT_LOGS`.
2. **Trigger `TRG_PREVENT_DEPT_DELETION_WITH_STAFF` (`BEFORE DELETE ON DEPARTMENTS FOR EACH ROW`)**
   * Verifies if any active employee is currently assigned to `:OLD.department_id`.
   * Enforces a clean user-defined error (`RAISE_APPLICATION_ERROR(-20002, 'Cannot delete department with active personnel.')`).

### Task S3: PL/SQL Stored Procedure — `SP_TRANSFER_EMPLOYEE_DEPT`
* **File:** `sql/shobit_04_review2_plsql.sql`
* **Signature:**
  ```sql
  CREATE OR REPLACE PROCEDURE SP_TRANSFER_EMPLOYEE_DEPT (
      p_employee_id       IN  NUMBER,
      p_new_department_id IN  NUMBER,
      p_result_message    OUT VARCHAR2
  );
  ```
* **Execution Logic:**
  1. Validates employee existence; handles `NO_DATA_FOUND`.
  2. Validates new department existence.
  3. Checks that employee is not already in that department.
  4. Executes `UPDATE EMPLOYEES SET department_id = p_new_department_id WHERE employee_id = p_employee_id;`.
  5. Returns formatted confirmation string with target building location.

### Task S4: PL/SQL Stored Function — `FN_GET_TECH_WORKLOAD_SCORE`
* **Purpose:** Computes the operational load of a given technician.
* **Signature:**
  ```sql
  CREATE OR REPLACE FUNCTION FN_GET_TECH_WORKLOAD_SCORE (
      p_technician_id IN NUMBER
  ) RETURN NUMBER;
  ```
* **Logic:** Returns total active tickets resolved and currently investigated by the technician.

### Task S5: Explicit Cursor & Staff Allocation Report
* **Purpose:** Generates a department-by-department staffing balance report.
* **Logic:**
  1. Parameterized cursor: `CURSOR c_dept_staff (cp_dept_id NUMBER) IS SELECT full_name, role FROM EMPLOYEES WHERE department_id = cp_dept_id;`.
  2. Loops through departments, counting users vs technicians, and outputs warning if a department has 0 support staff.

### Task S6: Database Views & Set Operations
* **View `V_PUBLIC_STAFF_DIRECTORY` (`WITH READ ONLY`):** Secure view that masks sensitive employee internal identifiers while exposing building locations and department phone extensions.
* **Set Operations Script (`shobit_05_review2_views.sql`):**
  * `MINUS`: Finds departments that currently have no technicians assigned:
    ```sql
    SELECT department_id, department_name FROM DEPARTMENTS
    MINUS
    SELECT DISTINCT d.department_id, d.department_name 
    FROM DEPARTMENTS d JOIN EMPLOYEES e ON d.department_id = e.department_id 
    WHERE e.role = 'TECHNICIAN';
    ```
  * `INTERSECT`: Identifies personnel roles meeting complex operational criteria.
